# 风险诊断手册（症状 → 根因 → 动作）

> 当用户反馈异常时，先在下表定位根因与对应阶段，再执行"动作"列。动作完成后，回到正常的五阶段流程继续推进。

## 一、快速诊断表

| # | 症状（用户原话） | 根因 | 定位阶段 | 动作 |
|---|---|---|---|---|
| D1 | "做出来的不是我要的" | 规格缺失——预期从未写成文字 | ② 产品设计 | 补做产品设计文档：与用户逐项确认功能边界，产出"做什么 / 不做清单"（模板：assets/product-design-template.md） |
| D2 | "AI 自己加了一堆我没要的功能" | 缺乏范围约束 | ② | 明确 MVP 边界；在 AGENTS.md 加入边界约定（不擅自扩大需求范围，规格不明先提问） |
| D3 | "改好一个、坏了两个" / "回不去了" | 无版本管理 | ① / ④ | 立即 `git init`（或补建提交规范），恢复到最后可用版本，确立"每次改动一个 commit"规则 |
| D4 | "我天天在帮 AI 找 Bug" | AI 无自测能力 | ④ | 为 AI 配置验证工具（Codex：Computer Use + Chrome 插件；其他工具配对应能力），AGENTS.md 写入测试规则 |
| D5 | "AI 说测试都过了，一跑就报错" | 测试覆盖不到真实路径（**属正常现象**） | ④ → ⑤ | 走人工验证：冒烟测试 + 现场报错原样反馈修复；不要因一次报错否定整个流程（反馈单见 assets/issue-report-template.md） |
| D6 | "修了好几次还是不对" | "预期本身"有问题（非实现 bug） | ⑤ → ②③ | 触发规格修订回路：先改产品设计 / 技术方案文档，再重新实现——禁止绕开文档直接改代码 |
| D7 | "越聊越糊涂，AI 开始发散" | 上下文过载 | 全流程 | 新开会话；把已有共识落进文档，让 AI 从文档而不是对话里取上下文 |
| D8 | "技术选型错了，要推倒重来" | 跳过技术设计 | ③ | 补做技术方案评审：候选方案 → 优缺点 → 备选 → 结论，写入 docs/tech-design.md |
| D9 | "文档和代码对不上" | 规格变更未回写 | ⑤ → ②③ | 强制回写文档后再改实现；建立"规格变更是文档变更"的规则 |
| D10 | "项目越做越臃肿，没法维护" | 放任 AI 自行设计功能与架构 | ② | 用"不做清单"和边界约定做硬约束；长期项目建议写 spec 硬规范（明确技术选型与需求范围） |
| D11 | "交互体验很差 / 边界情况总出问题" | 验收盲区 | ⑤ | 按验收清单三件套走查：主流程 → 边界情况 → 交互体验；后端重的项目应前置 Demo 验证交互 |

## 二、护栏缺失时的"三步补救"

当诊断出项目缺少基础护栏时，按顺序补救（不必推倒重来）：

1. **补版本管理**：`git init` + 提交当前可用版本作为基线 → 确立"每改动一 commit"规则；
2. **补 AGENTS.md**：写入交付硬规则（commit + 测试 + commit 信息语种），补充运行 / 测试命令（模板：assets/AGENTS.template.md）；
3. **补自测能力**：为 AI 工具配置运行、页面检查、测试能力，让 AI 在交付前先自检。

> 补救也可通过 `python scripts/init_project.py <项目目录>` 完成——脚本对已有目录与已有仓库是安全的（不覆盖已存在文件、不重复 init）。
> 补救完成后，可用 `python scripts/check_project.py <项目目录>` 复查护栏状态。

## 三、诊断输出格式建议

向用户汇报诊断结论时，按以下结构组织：

```
【症状】用户报告的问题（原话复述）
【根因】判断依据（对应 D# 条目）
【定位】问题发生的阶段 + 影响的护栏
【动作】1) ... 2) ... 3) ...
【回归】完成动作后如何验证问题已解决
```
