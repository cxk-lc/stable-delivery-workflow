## 一、总览

### 1.1 要解决的问题

把需求交给 AI 后，常见三种失败：

1. **交付物偏离预期**——"做出来的不是我想要的"；
2. **无法运行或缺陷密集**——"连启动都过不了"；
3. **越改越乱**——"修好一个、坏了两个，还无法回退"。

三种失败对应三类偏差：

| 偏差类型 | 典型表现 | 根因 |
|---|---|---|
| 方向偏差 | 功能不符合预期、过度设计 | "预期"从未被写成明确规格（做什么 / 不做什么） |
| 实现偏差 | Bug、跑不起来 | AI 缺少验证手段，错误在交付前未被暴露 |
| 验收偏差 | 能用但不好用、边界踩雷 | 缺少真实使用者视角的最终确认 |

### 1.2 方法论内核：五阶段闭环 + 三重护栏

**五阶段闭环**：

```
① 环境搭建 → ② 产品设计 → ③ 技术设计 → ④ 产品实现 → ⑤ 人工验证
  （一次性基座）        ↑____________反馈回路____________|
```

**三重护栏**（任何规模的项目都必须保留）：

| 护栏 | 内容 | 解决的问题 |
|---|---|---|
| 可回退 | Git 版本管理（每功能一个 commit，建议同步远端） | 改坏了回不去 |
| 可自检 | 给 AI 配置验证工具（运行、页面检查、测试） | 人沦为"人工测试员" |
| 可验收 | 人工亲自试用后才算完成 | 验收盲区 |

**一句话总纲**：在"可回退、可自检、可验收"的护栏内，用"规格 → 实现 → 验证"的闭环，把 AI 的生成能力转化为稳定的交付能力。

### 1.3 流程裁剪：什么时候走全套，什么时候走捷径

| 需求类型 | 建议路径 |
|---|---|
| 简单 / 不重要 / 试错性质 | 精简路径：① 环境（复用）→ ④ 实现（AI 自测）→ ⑤ 人工验证 |
| 复杂 / 重要 / 高风险 | 完整路径：①→②→③→④→⑤ 全部走完 |

- 判断依据：**需求复杂度、重要性、失败成本**（做砸了的代价有多大）；
- 唯一不可裁剪的部分：三重护栏；
- 权衡逻辑：参与度越高 → 可控性越强、速度越慢；交给 AI 的决策越多 → 越快、偏离预期的概率越高。

### 1.4 角色定义「延伸」

> 视频为"单人 + AI"场景；下表将其抽象为职能角色，供团队参考。单人场景可一人分饰多角，但心理上要明确"此刻戴的是哪顶帽子"（尤其验收时不要用实现者的心态）。

| 角色 | 核心职责 | 关键产出 |
|---|---|---|
| 产品负责人 | 定义"做什么 / 不做什么"，确认 MVP 边界 | 产品设计文档（确认版） |
| 技术负责人 | 决定技术路线与架构方向，评审备选方案 | 技术方案文档（确认版） |
| 开发者（驱动者） | 驱动 AI 执行、监督过程、反馈问题、管理提交 | 可运行版本 + 提交历史 |
| 验收者 | 以真实使用者身份完成最终验收（团队中建议非主要实现者） | 验收结论 |
| AI Agent | 方案建议、执行实现、运行自测、整理文档；**不承担决策与责任** | 代码、测试、自测报告 |

**责任总则**：AI 是能力放大器，不是责任主体；所有交付责任由对应人类角色承担。

## 二、五阶段详解

> 每阶段按统一结构展开：目标 / 输入 / 核心活动 / 输出与交付物 / 参与角色 / 完成标准 / 衔接关系 / 关键提示。

### 阶段一：环境搭建（Environment Setup）

**定位**：项目级一次性基座——在产生任何代码之前，为整个项目建立"可回退 + 可自检"的护栏。

**目标**：让 AI 在受控环境中工作——产出可追踪、改动可回退、行为受规则约束。

**输入**：项目立项信息（一句话级别的想法描述即可）。

**核心活动**：

1. 创建项目专属文件夹；在 AI 编程工具（如 Codex）中新建本地项目并关联该目录。
2. **初始化 Git 仓库**：执行 `git init`，用 `git status` 验证；建议关联 GitHub 等远端仓库，防止本地故障连历史一起丢失。
3. **创建 AGENTS.md**（项目"值班手册"，AI 每次新会话优先读取），写入交付硬规则（模板见附录 B）：
   - 每次改动后必须创建对应的 Git commit；
   - 每次改动后必须编写 / 更新相关测试，交付前确保全部测试与验收通过；
   - 所有 commit 信息统一使用约定语种（未指定时默认采用用户当前系统语言，可自行指定）。
4. 创建首次提交前，先与用户确认 commit 信息使用的语种（未指定时默认采用用户当前系统所使用的语言：Windows 取系统 UI 语言；macOS / Linux 取 LANG、LC_* 环境变量，检测失败回退简体中文），并将结果写入 AGENTS.md 交付规则；然后提交首次 commit，形成版本基线。
5. **配置 AI 的验证工具**：安装运行 / 页面检查类能力（Codex 为 Computer Use + Chrome 插件；其他 Agent 配置对应工具或 Skill）。*视频中此步放在实现之前，建议提前到本阶段一并完成。*

**输出与交付物**：

| 交付物 | 说明 |
|---|---|
| Git 仓库（含首次 commit） | 可回退的版本基线 |
| AGENTS.md | 交付规则的唯一入口文件 |
| AI 工作环境 | 项目已导入 AI 工具、验证工具就绪 |

**参与角色**：开发者（执行与确认）；AI Agent（执行初始化指令）。

**完成标准（DoD）**：

- [ ] `git status` 显示仓库状态正常
- [ ] AGENTS.md 已创建且内容正确
- [ ] AI 具备验证其产出结果的能力（能运行、能查看页面）

**衔接关系**：无前置依赖；是阶段二~五的公共基座，**全项目只做一次**。

**关键提示**：环境搭建只有两件事（Git + AGENTS.md），却解决两个高频风险——代码改坏可退、交付前先自检。AGENTS.md 要精简可执行，写成"项目百科全书"反而让 Agent 丢失重点。

### 阶段二：产品设计（Product Design，回答 What）

**定位**：把模糊想法压缩成可验证的 MVP 边界——第一次把"预期"写成文字。

**目标**：产出明确、简短、经确认的产品设计文档，确定"做什么 / 暂时不做什么"。

**输入**：产品想法 / 需求描述；阶段一就绪的环境。

**核心活动**：

1. **MVP 讨论**：与 AI 讨论"第一版应该包含哪些功能"（提示词见附录 C-1）。MVP = 只做最核心必要的功能，先跑通主流程。
2. **逐项砍范围**：对 AI 建议的每个功能问"没有它，主流程还能跑通吗？"——示例：EPUB 解析复杂 → 首版只支持 TXT；TXT 无目录概念 → 删除目录 / 章节功能；三种主题 → 只留明亮主题；书签不影响主流程 → 砍掉。
3. **补充边界条件**：请 AI 列出隐含边界与"可推迟清单"（示例：仅支持 UTF-8、纵向滚动不分页、大文件加载提示），逐项确认采纳。
4. **整理产品设计文档**：指示 AI 将共识整理成文档（不用太详细，梳理整体方向与主要功能即可，见附录 C-2），人工确认无误。
5. **（可选）制作 Demo**：只做前端界面、数据模拟，用于提前验证界面与交互（见附录 C-3）。

**关键决策点：是否先做 Demo**（判断依据为后端实现成本）：

| 判断维度 | 先做 Demo | 直接实现 MVP |
|---|---|---|
| 后端成本 | 高（涉及文件处理、搜索、模型调用等） | 低（如仅导入本地文本文件） |
| 理由 | 避免在错误的交互设计上投入大量实现 | 直接迭代更高效 |
| 示例 | 个人知识库（先做 Demo） | 电子书阅读器 TXT 版（跳过 Demo） |

**输出与交付物**：

| 交付物 | 说明 |
|---|---|
| 产品设计文档 | MVP 边界、功能清单、"明确不做的事"、已知边界条件 |
| （可选）可操作 Demo | 前端界面 + 模拟数据，用于确认交互流程 |

**参与角色**：产品负责人（决策砍功能、确认文档）；AI Agent（提建议、补边界、整理文档）。

**完成标准（DoD）**：

- [ ] "做什么 / 不做什么"清单明确且经确认
- [ ] 用户核心路径（主流程）清晰
- [ ] 文档简短、方向一致（细节留给迭代）
- [ ] 若做了 Demo：界面与交互已确认

**衔接关系**：依赖阶段一；其输出（产品设计文档）是阶段三的直接输入；与阶段三输出共同构成阶段四的"轻量规格"；Demo 是阶段五的前置验证手段（提前暴露交互问题）。

**关键提示**：第一条提示词很难直接长出好规格——人必须读完 AI 的建议，砍掉过度设计、补上隐含边界，再把共识写进文档。产品文档像"施工图"，后续所有工作以同一张图为准。

### 阶段三：技术设计（Technical Design，回答 How）

**定位**：锁定技术路线与架构大方向，防止方向性返工。

**目标**：确认技术栈与架构方向正确，产出可供实现直接引用的技术方案文档。

**输入**：产品设计文档。

**核心活动**：

1. **新开会话**讨论（隔离旧上下文，讨论更聚焦）。
2. 让 AI 阅读产品设计文档并给出技术栈建议（示例：直接在讨论中询问候选技术是否合适，见附录 C-4）。
3. **评估建议与备选**：要求 AI 同时说明优势、缺点与替代方案（示例：Electron 的缺点 + Tauri 备选），由技术负责人决策。
4. **写技术方案文档**：指示 AI 写入 `docs/` 目录（见附录 C-5），记录技术栈、架构方向与取舍理由。

**输出与交付物**：

| 交付物 | 说明 |
|---|---|
| 技术方案文档（docs/） | 技术栈、架构方向、关键取舍、备选方案记录 |

**参与角色**：技术负责人（决策）；AI Agent（提供建议与撰写文档）。

**完成标准（DoD）**：

- [ ] 技术栈确定且选择理由明确
- [ ] 大方向正确（无需细节完备，细节在实现中校准）
- [ ] 已知风险与备选方案有记录

**衔接关系**：依赖阶段二；与产品设计文档共同构成阶段四的输入（"轻量规格 spec"）。

**关键提示**：不要追求覆盖每个类与接口的厚文档——过早写满细节，等于把尚未验证的猜测包装成约束。文档颗粒度应与项目阶段匹配：MVP 阶段只需确认"技术路线不会走偏"。

### 阶段四：产品实现（Implementation）

**定位**：在护栏内让 AI 完成实现与自测——AI 是主力，人是监督者与反馈者。

**目标**：产出可运行、已自测、已提交的 MVP 版本。

**输入**：产品设计文档 + 技术方案文档；就绪的 AI 验证工具。

**核心活动**：

1. **确认 AI 自测能力**：验证工具已安装 / 已开放（见阶段一第 5 条）。
2. **新会话实现**：指示 AI 阅读两份文档并按要求实现产品（见附录 C-6）。
3. **AI 自测**：AI 按 AGENTS.md 规则自测、修复，交付时报告测试与验收结果。
4. **人工冒烟测试**：人按说明实际运行（如 `npm start`）——**视频实测此处暴露了启动报错**。
5. **反馈修复**：把现场现象原样反馈给 AI（含操作步骤与报错原文，见附录 C-7）→ 修复 → 复验。

**输出与交付物**：

| 交付物 | 说明 |
|---|---|
| 可运行的 MVP 版本 | 能启动、主流程可操作 |
| 测试代码 | 与功能同步更新（AGENTS.md 强制） |
| 提交历史 | 每个改动一个 commit，可回溯、可回退 |
| 自测报告 | AI 交付时附带的测试与验收说明 |

**参与角色**：开发者（安装工具、监督、反馈）；AI Agent（实现 + 自测 + 修复）。

**完成标准（DoD）**：

- [ ] AI 自测全部通过且已提交证据
- [ ] 人工冒烟测试通过（能启动、主流程可走通）
- [ ] 每个改动均有对应 commit

**衔接关系**：依赖阶段二、三的文档；产出交付阶段五验收；**若实现中发现"规格本身"的问题，必须回到阶段二 / 三修订文档，不得绕过文档直接改实现**。

**关键提示**：只让 AI 写代码而不提供验证手段，人就会沦为"人工测试员"（AI 写一轮、人找一个 Bug、AI 再修一轮）。同时记住：**AI 自测通过 ≠ 无 Bug**——视频中 AI 自测全部通过后，首次人工启动仍然报错。自测的边界是"覆盖已知规则"；真实使用还会碰到体验问题、环境差异与未想到的路径。

### 阶段五：人工验证（Human Verification）

**定位**：以真实使用者身份完成最终验收——验收单只能由人签。

**目标**：确认产品在真实使用中符合预期；或把差距反馈回实现 / 规格，形成闭环。

**输入**：可运行的 MVP 版本。

**核心活动**：

1. **真实使用走查**：亲自操作，覆盖三块——主流程走查、边界情况、交互体验。
2. **问题记录与反馈**：记录现象（复现步骤 + 报错原文），原样反馈给 AI。
3. **修复与回归**：AI 修复 → 重新验证 → 确认没有改坏其他功能。
4. **规格判定**：若问题源于"预期本身"（而非实现 bug）→ 回到阶段二 / 三修订文档，再重新实现。

**输出与交付物**：

| 交付物 | 说明 |
|---|---|
| 验收记录 | 测试路径、发现的问题、修复确认 |
| 可交付版本 | 通过验收的稳定版本 |
| （如有）规格修订记录 | 回写到产品 / 技术文档的变更 |

**参与角色**：验收者（必须由人执行，团队中建议非主要实现者）；AI Agent（修复）。

**完成标准（DoD）**：

- [ ] 主流程在目标使用场景下符合预期
- [ ] 关键边界情况可接受
- [ ] 已知问题全部处理完毕或明确记录在案

**衔接关系**：五阶段闭环的终点，有三个出口——修复回路（→ 阶段四）、规格修订回路（→ 阶段二 / 三）、迭代回路（新功能从阶段二重新开始）。

**关键提示**：交互体验与不易想到的边界情况最容易遗留；AI 不可能覆盖所有问题，产品好不好用最终只能由人试过才知道。

## 三、阶段衔接与依赖关系

### 3.1 依赖链路全景

```
① 环境搭建（一次性基座：Git 仓库 / AGENTS.md / 验证工具）
     │ 提供护栏，全程生效
     ▼
② 产品设计 ──产品设计文档──▶ ③ 技术设计 ──技术方案文档──▶ ④ 产品实现 ──可运行版本──▶ ⑤ 人工验证
     ▲                        ▲                            │                      │
     │                        │                            └── 修复回路（缺陷反馈）──┘
     └────────── 规格修订回路（预期问题反馈）───────────────┘
     └────────── 迭代回路（新功能：从阶段二重新开始）──────────┘
```

### 3.2 阶段间依赖一览

| 衔接 | 依赖类型 | 载体（接口物） | 说明 |
|---|---|---|---|
| ① → ②~⑤ | 基础依赖 | Git 仓库 + AGENTS.md + 验证工具 | 一次性建立；后续所有阶段在此基座上运行 |
| ② → ③ | 顺序依赖 | 产品设计文档 | 技术方案必须基于已确认的产品边界 |
| ②③ → ④ | 联合输入 | 两份文档 = 轻量规格（spec） | AI 实现时必须同时读取两份文档 |
| ④ → ⑤ | 顺序依赖 | 可运行版本 + 自测报告 | 验收的前提是产品能跑、自测有证据 |
| ⑤ → ④ | 反馈回路（修复） | 缺陷现象描述（步骤 + 报错原文） | 实现缺陷 → 修复 → 回归验证 |
| ⑤ → ②③ | 反馈回路（规格修订） | 文档修订 | 预期问题 → 修订规格 → 重新实现 |
| ⑤ → ② | 迭代回路 | 新需求 | 新功能开发复用阶段二~五（环境不重建） |

### 3.3 三种反馈回路

1. **修复回路（⑤→④）**：高频、小步、快速闭环——适用于实现层面的 Bug。发现问题就反馈现场，修复后回归验证。
2. **规格修订回路（⑤→②③）**：当"不符合预期"源于预期本身（而非实现 bug）时启用。**严禁绕过文档直接口头改实现**，否则文档与实现漂移，AI 下次仍按旧文档产出。
3. **迭代开发回路（⑤→②）**：新功能从产品设计重新开始，走完整的②~⑤（环境无需重建）。

### 3.4 一次性与循环性

| 层级 | 范围 | 说明 |
|---|---|---|
| 一次性 | 项目级 | 仅阶段一（环境搭建） |
| 功能级循环 | 每个新功能 | 阶段二 → 三 → 四 → 五 |
| 微循环 | 每个功能内部 | ④ ↔ ⑤（实现 - 自测 - 修复），可重复多次 |

## 四、通用原则（贯穿全流程）

| 编号 | 原则 | 内涵 | 落地要点 |
|---|---|---|---|
| P1 | **规格先行** | 先让"预期"变成可检查的文字，再让 AI 实现 | 每个功能开工前确认：产品设计（要什么）+ 技术方案（怎么做）已就绪 |
| P2 | **护栏优先** | Git + AGENTS.md 在任何代码产生之前就位，且永不裁剪 | 项目第一天完成阶段一；测试规则不因赶进度而豁免 |
| P3 | **让 AI 自检** | AI 必须先自行发现问题，才把结果交给人 | 实现开工前，先确认 Agent 具备运行、页面检查、测试能力 |
| P4 | **人机分工清晰** | AI 负责生成、自测、整理；人负责意图、决策、验收 | 关键决策（砍功能、选技术栈、验收）不外包给 AI |
| P5 | **小步提交、可回退** | 每完成一个功能保存一个版本快照，任何时刻都能回到上一个正常节点 | commit 与功能一一对应；出错先回退再排查 |
| P6 | **文档即接口** | 阶段之间的交接物是文档，不是"口头共识"或"聊天记录" | 规格变化必须落到文档；AI 的输入永远是文档 |
| P7 | **按复杂度伸缩** | 流程深度 = f(复杂度, 重要性, 失败成本) | 开工前自问："这个需求做砸了的代价有多大？" |
| P8 | **证据驱动交付** | "完成"不是"代码写完了"，而是"可检查的验收条件全部满足" | 要求 Agent 交付时提交证据（测试结果、运行日志 / 截图） |
| P9 | **持续校准** | 这套流程是"当前模型能力下的合理实践"，不是永恒标准 | 随大模型进化定期复盘流程；作者本人亦声明此流程非唯一标准答案 |

## 五、最佳实践与注意事项

### 5.1 环境与工具

- AGENTS.md 只放**高频硬规则**，细节按需引用其他文档；写成"百科全书"会让 Agent 丢重点。
- 仓库同步到远端（GitHub 等），避免本地故障连历史一起丢失。
- 把运行命令、测试命令明确写入 AGENTS.md 或 README，让 Agent 可直接执行。

### 5.2 产品设计

- 砍功能时逐项自问："没有它，主流程还能跑通吗？"
- 边界条件（编码格式、滚动方式、异常提示等）主动让 AI 列清单，人工逐项采纳。
- Demo 只做界面与交互、数据模拟；是否制作以后端成本为准。
- 文档简短即可：方向一致优先于细节完备。

### 5.3 技术设计

- 新开会话讨论，避免旧上下文干扰。
- 要求 AI 同时给出优势、缺点与备选方案（决策需要取舍信息）。
- 记录取舍理由，方便日后复盘与迭代。

### 5.4 产品实现

- 开工前先跑通"AI 能看到结果"的验证链路（工具装好再动手）。
- 会话中明确指向文档路径（如"这个目录下有产品设计和技术方案两份文档"）。
- 报错反馈技巧：**原样描述现场**（含操作步骤与报错原文），不做二次转述、不加主观推测。
- 定期检查 commit 粒度，防止"一锅烩"式提交。

### 5.5 人工验证

- 验收前先问自己："如果我是第一次用这个产品的用户，我会怎么走？"
- 覆盖优先级：主流程 → 上次出问题的地方 → 容易出错的边界。
- 交互体验问题也要记录（不只是功能 Bug）。
- 每次修复后回归验证，确认没有改坏其他功能。

### 5.6 上下文与协作

- **新主题新会话**：技术设计、产品实现各自新开会话，减少旧上下文干扰。
- **术语统一**：需求中的核心名词先确认定义与范围，再展开讨论（避免歧义被 AI 放大）。
- **共识落文档**：重要结论写进文档，不要留在对话里——文档是 AI 跨会话的"记忆载体"。
- 长项目定期维护 AGENTS.md 与文档，保持它们是"活的"。

## 六、常见风险与应对

| # | 风险 | 典型表现 | 根因 | 应对措施 | 关联阶段 |
|---|---|---|---|---|---|
| R1 | 方向偏差 | 做出来的不是想要的 | 规格缺失 | 产品设计 + 逐项砍功能 + 文档确认 | ② |
| R2 | 功能膨胀 | AI 自行添加内容，项目臃肿难维护 | 缺乏硬约束 | MVP 边界 + 明确"不做什么"；长期项目建议用 spec 硬规范约束技术选型与需求范围 | ② |
| R3 | 改坏既有功能 | 修好一个、坏了两个 | 无版本管理 | Git + 每功能一 commit + 随时可回退 | ①④ |
| R4 | 人沦为人工测试员 | 频繁人工找 Bug，无法聚焦 | AI 无验证手段 | 配置 Computer Use / Chrome 等验证工具 | ④ |
| R5 | 自测通过仍有 Bug | 启动报错、边界崩溃 | 测试覆盖不到真实路径 | 人工验证 + 现场反馈修复（视频实测案例） | ⑤ |
| R6 | 交付无法运行 | 环境差异、依赖缺失 | 交付前未真实运行 | 人工冒烟测试 + 运行命令文档化 | ④⑤ |
| R7 | 技术选型返工 | 中期发现技术路线错误 | 跳过技术设计 | 技术方案评审 + 备选方案 + 取舍记录 | ③ |
| R8 | 文档与实现漂移 | AI 按过期文档实现 | 规格变更未回写 | 规格修订回路强制回写文档后再改实现 | ⑤→②③ |
| R9 | 上下文过载 | 会话变长后 AI 丢重点、开始"发散" | 单会话承载全部上下文 | 新会话隔离 + 文档承载共识 | 全流程 |
| R10 | 过度详尽的文档 | 未验证的猜测被包装成约束，束缚实现 | 提前细化 | 文档只锁大方向，细节后置到实现中校准 | ③ |
| R11 | 验收盲区 | 交互体验、边界情况被遗漏 | 自动测试无法覆盖体验 | 真实使用走查（主流程 + 边界 + 体验三件套） | ⑤ |

| 阶段 | 一句话 | 输入 → 输出 | 关键角色 |
|---|---|---|---|
| ① 环境搭建 | Git + AGENTS.md，一次性基座 | 项目想法 → 受控环境 | 开发者 |
| ② 产品设计 | 砍到 MVP，写成文档 | 想法 → 产品设计文档 | 产品负责人 |

**三重护栏**：可回退（Git）· 可自检（AI 自测）· 可验收（人工验证）——任何需求规模都不可裁剪。

**三条回路**：修复回路（⑤→④）· 规格修订回路（⑤→②③）· 迭代回路（⑤→②）。

**一条铁律**：AI 自测通过 ≠ 无 Bug。测试只能验证"代码是否符合预期"，不能替人判断"预期是否合理"。
