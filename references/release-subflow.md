# 发布子流程（可选）· Release Subflow

> **归属**：阶段五·人工验证的**可选子分支**，不是第六阶段，不改变五阶段闭环的成立条件。
> **权威关系**：触发时机 / 步骤 / 可选约束以本文件为准；阶段定位见 `references/methodology.md` 阶段五；执行期硬约束见 `SKILL.md`。
> **一句话**：发布是"验收之后的可选动作"，不是"闭环的必要条件"——跳过发布，流程照样完整结束。

---

## 1. 定位与边界

**是什么**：把"已验收通过的版本"变成"可对外分发的版本"——打 annotated tag、归档发布记录、（可选）推送远端与创建 Release。

**不是什么**：

- 不是阶段六。阶段编号始终于五，闭环判定仍以阶段五的验收结论为准；
- 不是闭环必要条件。未发布 ≠ 未完成；
- 不是代码变更窗口。子流程内不实现功能、不修复缺陷。

**三条硬边界**：

1. **只发布，不改码**——子流程内发现缺陷，必须回流阶段四修复并重新验收，不得"顺手修好再打标签"；
2. **只读已验收产物**——tag 必须指向已签署验收的那个 commit；
3. **外部动作二次确认**——推送远端、创建 Release 属外部可见动作，必须由用户显式确认目标远端与版本号。

---

## 2. 触发时机（唯一入口）

触发点 = 阶段五末尾的**收口询问（Stage 5 Exit Gate）**。必须以下三条**同时成立**才询问：

| 编号 | 前置条件 | 判定依据 |
|---|---|---|
| P1 | 验收清单逐项勾选完毕 | `docs/acceptance-checklist.md` 的冒烟 / 主流程 / 边界 / 交付物四节均为 `[x]` |
| P2 | 验收结论已由人签署 | 结论（通过 / 有条件通过）+ 验收人 + 日期均已落字 |
| P3 | 无未处理问题 | 已登记问题要么修复并回归验证，要么明确写入"遗留问题" |

**时机约束**：

- **只在验收达成之后询问**，不得提前。验收未完成就问"要不要发布"，等于用发布替代验收；
- **每轮验收达成询问一次**，不得重复追问（用户已选跳过，本次不再提，见 CN7）；
- **"有条件通过"可以进入询问**，但遗留问题必须写入发布记录的「已知问题」，且默认建议预发布标签（如 `v1.2.0-rc.1`）；
- 验收结论为「不通过」时**不询问**——回到修复回路（→ 阶段四）或规格修订回路（→ 阶段二 / 三）。

## 3. 与主流程的衔接

### 3.1 分流关系

```
阶段五 · 人工验证（5A，闭环必需）
   │
   ├── 验收未通过 ──▶ 修复回路（→④）／规格修订回路（→②③）
   │
   └── 验收达成（P1–P3 满足）
          │
          └── 收口询问「是否需要执行发布？」  ← 必须问一次，不得默认
                 │
                 ├── 否：跳过 ──────────────▶ 闭环结束（不产生任何发布产物）
                 ├── 仅本地：打 tag 不推送 ──▶ 闭环结束（轻量留痕）
                 └── 是：发布子流程（S1–S5）─▶ 闭环结束
```

### 3.2 接口物（交接载体）

| 方向 | 载体 |
|---|---|
| 进入 | 已签 `docs/acceptance-checklist.md`（结论 = 通过 / 有条件通过）+ 自测证据（如 `docs/self-test-report.md`）+ 工作区干净的 commit |
| 退出 | annotated tag `vX.Y.Z` + `docs/release-record.md` 追加一节 +（若选择推送）远端 refs |

### 3.3 闭环判定（关键语义）

| 用户选择 | 五阶段闭环是否成立 | 判定依据 |
|---|---|---|
| 跳过发布 | **成立** | 验收结论已签 = 交付闭环达成；发布产物为空属预期 |
| 只打本地 tag | **成立** | 同上，另留本地基线 |
| 完整发布成功 | **成立** | 同上，另留发布产物 |
| 完整发布中途失败 | **成立**（标注"发布未完成"） | 验收闭环已成立；发布属运维动作，其失败不回退验收结论 |

> **一句话**：**发布成败不改变闭环判定**；只有验收未通过才使闭环不成立。

### 3.4 与其它回路的关系

- **发现缺陷** → ⑤→④ 修复回路：子流程就地暂停，修复并回归验收后从 S2 重做发布前检查；
- **发现预期问题** → ⑤→②③ 规格修订回路：先改文档再重实现，回来后重新验收；
- **发布完成** → 本次 tag 成为下一轮迭代（→②）的回滚基线；
- **禁止**：在子流程内直接改代码、改规格文档、改验收结论。

## 4. 子流程步骤

| 步骤 | 动作 | 产物 | 失败 / 异常处理 |
|---|---|---|---|
| **S0 选择确认** | 执行收口询问，三选一：立即发布 / 仅本地留痕 / 跳过 | 选择记录（写入验收清单） | 用户未明确 → 按"跳过"处理，不代替用户决策 |
| **S1 版本号判定** | 按语义化规则给出建议（patch / minor / major，是否加预发布后缀）并说明理由 | 版本号 `vX.Y.Z` | 用户未确认 → 停在 S1，不自行决定版本号 |
| **S2 发布前检查** | 工作区干净（`git status`）／分支正确／`HEAD` 与验收记录一致／测试证据在案／无 `.env` 与密钥入库 | 检查结论 | 任一项不通过 → 停止并回到对应阶段，不强行发布 |
| **S3 打标签** | `git tag -a vX.Y.Z -m "vX.Y.Z"`，指向验收通过的 commit | annotated tag | 打错 → `git tag -d vX.Y.Z` 后重打，不得强行移动已有 tag |
| **S4 归档记录** | 按 `assets/release-record-template.md` 追加 `docs/release-record.md` → 提交该记录 | 发布记录 commit | 记录缺失 → 视为"发布未完成" |
| **S5 推送与外发（可选）** | `git push origin <branch> --follow-tags`；创建 Release 需再次确认 | 远端 tag / Release | 推送失败 → 保留本地 tag，记录中标注"仅本地" |

**顺序约束（易错点）**：默认**先提交发布记录、再打 tag**，否则 tag 指向的树里没有发布记录。若团队约定"tag 必须精确指向验收时的 commit"，则改为：tag 打在验收 commit → 记录放其后 commit → 在记录中写明 tag 指向的 commit hash。**二选一，写入 `AGENTS.md` 保持一致**，不要两种混用。

## 5. 非强制性的可选约束（CN1–CN9）

> 这九条是"可选"含义的完整定义；违反其中任何一条，都会让可选子流程事实上变成强制流程。

| 编号 | 约束 | 落地含义 |
|---|---|---|
| CN1 | **默认不做** | 跳过发布是合法终点：不视为未完成、不记为缺陷、不触发告警 |
| CN2 | **不计入 DoD** | 阶段五 DoD 的「必需项」不含任何发布条目；发布只作为「条件项」 |
| CN3 | **不计入通过率** | `scripts/check_project.py` 对发布仅输出提示（ℹ），不改变通过项计数与退出码 |
| CN4 | **可延迟** | 验收后任意时点可补做；补做时重新确认目标 commit 与版本号 |
| CN5 | **可部分执行** | 允许"只打本地 tag 不推送"或"只归档记录不打 tag"，但必须在记录中标注实际状态，**不得声称已发布** |
| CN6 | **可撤销** | 中途放弃：`git tag -d vX.Y.Z`；已推送则 `git push origin :refs/tags/vX.Y.Z`；记录标注"已撤销"，该版本号不复用 |
| CN7 | **问一次不追问** | 主流程有"必须问一次"的义务；用户选跳过即视为已决策，除用户主动要求或下一轮验收达成外不再询问 |
| CN8 | **不阻塞迭代** | 未发布不得阻塞下一轮功能迭代；新功能不要求上一版已发布 |
| CN9 | **人定版本号** | AI 只给语义化建议与理由；版本号、目标远端、是否外发均由用户确认 |

**另有一条建议（非强制）**：长期不对外发布的仓库，建议至少留一个可回退基线（如 `git tag -a snapshot-YYYYMMDD`），便于日后追溯"哪次验收对应哪段代码"。缺失不影响闭环。

## 6. 子流程 DoD（条件项）

仅当用户选择「立即发布」或「仅本地留痕」时核对；未满足只说明**发布未完成**，不影响**交付已闭环**。

- [ ] tag 为 annotated（`git tag -a`），且 `git rev-parse vX.Y.Z^{commit}` 等于验收通过的 commit
- [ ] `docs/release-record.md` 已追加本节：变更摘要 / 验证证据 / 已知问题 / 回滚指令
- [ ] 工作区干净，无密钥与敏感数据入库
- [ ] 若选择推送：远端存在同名 tag；若未推送：记录中已标注"仅本地"
- [ ] 验收清单中「是否发布」一栏已按实际选择填写

---

## 7. 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 把发布写进必需 DoD | "未上线 = 未完成"，闭环永远不成立 | 发布列为条件项（CN2） |
| 验收没签就问发布 | 用发布替代验收，验收盲区被掩盖 | 严守 P1–P3 前置条件 |
| 子流程里顺手修 bug | tag 指向未经回归的代码 | 回流阶段四，修完重新验收 |
| 先打 tag 再写记录 | tag 内缺发布记录 | 先 commit 记录再打 tag（或记录中注明 hash） |
| 跳过发布后反复追问 | 打扰用户、流程噪音 | 问一次（CN7） |
| AI 自定版本号直接推送 | 外部可见错误难以撤回 | 版本号与推送由人确认（CN9） |

## 8. 参考命令

```bash
# S2 发布前检查
git status --porcelain          # 应为空
git rev-parse HEAD              # 与验收记录中的 commit 比对

# S3 打 annotated tag（指向当前已验收 commit）
git tag -a vX.Y.Z -m "vX.Y.Z"

# S4 归档后再提交记录，然后确认 tag 指向
git add docs/release-record.md && git commit -m "docs: 发布记录 vX.Y.Z"
git rev-parse vX.Y.Z^{commit}

# S5 推送（可选）
git push origin <branch> --follow-tags

# CN6 撤销
git tag -d vX.Y.Z
git push origin :refs/tags/vX.Y.Z    # 仅在已推送时
```
