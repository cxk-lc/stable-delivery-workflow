# 各阶段提示词模板

> 源自实战视频演示，已泛化为模板；`{ }` 为占位符。均可直接复制给 AI 编程工具（Codex / Claude Code / Cursor 等）使用。
> 使用要点：**一次只推进一个阶段**；AI 给建议后，由人决策、砍范围、确认文档。

---

## C-1 产品设计 · MVP 讨论（阶段二）

```
我想做一个{产品类型}，打算先从 MVP 版本开始。
请按 must / should / could / won't 四档给出功能建议，并逐项说明：
没有它，主流程还能跑通吗？先不要展开实现细节。
```

**用法**：拿到 AI 的分档建议后，**逐项砍范围**——重点保留 `must`，把 `should/could` 放入"不做清单"或下一版；每个功能都问"没有它，主流程还能跑通吗？"。示例：EPUB 解析复杂 → 首版只支持 TXT；三种主题 → 只留明亮主题；书签 → 延后。

---

## C-2 产品设计 · 整理文档（阶段二）

```
请把刚才讨论的内容整理成一份产品设计文档，不用太详细，
梳理整体方向和主要功能即可。
```

**用法**：配合 `assets/product-design-template.md` 使用；产出存为 `docs/product-design.md`，由用户确认后才进入下一阶段。

---

## C-3 产品设计 · 制作 Demo（可选，阶段二）

```
帮我做一个 Demo，不用实现真实的后端功能，数据模拟一下就行。
我主要是想看看整体界面和操作流程是否合理。
```

**用法**：判断标准是**后端实现成本**——后端重（文件处理、搜索、模型调用等）先做 Demo；后端轻（如仅导入本地文本）直接做完整 MVP。

---

## C-4 技术设计 · 方案讨论（阶段三）

```
请先读 docs/product-design.md。
然后给我 2-3 个技术栈候选方案，分别说明优点、缺点、适用场景和主要风险；
不用给出过于详细的设计，我们先探讨。
我听说{候选技术}还可以，它和其他候选相比如何？
```

**用法**：建议**新开会话**执行此提示词（隔离旧上下文）；先让 AI 给候选与取舍，再提你听说的方案，避免被单一候选锚定。决策需要取舍信息，而不是一句"可以用"。

---

## C-5 技术设计 · 写方案文档（阶段三）

```
请把刚才讨论的技术方案整理成一份文档，放在 docs 文件夹中。
```

**用法**：配合 `assets/tech-design-template.md` 使用；只锁大方向，不要求细节完备。

---

## C-6 产品实现 · 实现产品（阶段四）

```
请先读 AGENTS.md 了解项目规则，再读 docs/product-design.md 与 docs/tech-design.md。
按这两份文档实现产品；实现后运行测试，并报告测试命令、结果、截图/日志和对应的 commit。
```

**用法**：开工前确认 AI 已具备自测能力（运行、页面检查、测试）；实现完成后要求 AI 报告自测结果，随后安排人工冒烟测试。只有"读了 AGENTS.md + 双文档 + 提交证据"才算完成实现阶段。

---

## C-7 人工验证 · 反馈报错（阶段四 / 五）

```
{描述操作步骤}之后，直接显示了一个报错：{报错原文}。
```

**示例**："打开之后，直接显示了一个报错：操作失败，请稍后重试。"

**用法要点**：**原样描述现场**——含操作步骤与报错原文，不做二次转述、不加主观推测，让 AI 拿到第一手信息。修复后必须复验。

**完整版模板**：`assets/issue-report-template.md`（含环境信息 / 复现频率 / 期望 vs 实际 / 边界说明）。

---

## C-8 发布子流程 · 发布前检查与版本号建议（阶段五 · 可选）

```
进入发布前检查。先不要打标签、不要推送，只做检查并报告：
1) git status 是否干净、当前分支、HEAD 的 commit hash；
2) 验收清单与自测报告是否在案，验收结论是否为「通过 / 有条件通过」；
3) 对照 CHANGELOG 与最近提交，建议版本号（patch / minor / major）并说明理由；
4) 列出发布将执行的具体命令（打 tag、归档发布记录、推送），等我确认后再执行。
```

**用法**：

- **触发时机**：仅在验收结论已签署、无未处理问题之后使用（P1–P3 满足）。**验收未完成不得进入发布**——那等于用发布替代验收。
- **可选语义**：不需要发布时**不必执行本模板**，直接结束流程即可：不留发布产物、不记为未完成、不计入任何通过率。
- **人工确认点**：版本号、目标远端、是否推送由人决定；确认前 AI 只做检查与建议，不得自行打 tag 或推送。
- **只发布不改码**：检查中发现缺陷 → 回流阶段四修复并重新验收，不在发布窗口内顺手改码。

**完整步骤与可选约束**（S0–S5、CN1–CN9、反模式）：`references/release-subflow.md`。

## 通用技巧

| 技巧 | 说明 |
|---|---|
| 新会话隔离 | 技术设计、产品实现各自新开会话；重要共识写进文档，不依赖对话记忆 |
| 术语统一 | 讨论前先确认核心名词的定义与范围，避免歧义被 AI 放大 |
| 指向文件 | 指令中写明确切路径（`AGENTS.md`、`docs/product-design.md`、`docs/tech-design.md`），不要用"这个目录下有两个文件"这类模糊指代 |
| 阶段收口 | 每个阶段产出交付物后暂停，核对 DoD 再推进，不要一口气跑到黑 |
| 决策留给人 | AI 只出建议；砍功能、选技术栈、验收结论、是否发布由人确认 |
| 可选动作先问后做 | 发布等外部可见动作：先检查与建议，等确认再执行；跳过路径不产出任何文件 |
