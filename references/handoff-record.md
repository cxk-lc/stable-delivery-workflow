# 开发进度交接记录 · Handoff Record

> **归属**：阶段四（产品实现）的必需产物，同时支持独立调用（不改代码，只生成交接文档）。
> **权威关系**：结构、场景判定、提交门禁以本文件为准；阶段定位见 `references/methodology.md` 阶段四；执行期硬约束见 `SKILL.md`。
> **一句话**：把"这次做到哪、为什么这么做、下一步做什么"写成文件，让下一次会话不依赖聊天记忆。

---

## 1. 定位与边界

**是什么**：

- 阶段四的进度载体：开工时建立，开发中随每次 commit 更新；
- 跨会话交接接口：新会话先读 `docs/handoff-record.md`，再读双设计文档；
- 独立功能：任何时点都可单独调用脚本生成/刷新，不要求正在走五阶段流程。

**不是什么**：

- 不是设计文档的替代品。规格仍以 `docs/product-design.md` 与 `docs/tech-design.md` 为准，交接记录只描述"进度与决策"；
- 不是提交日志的复制品。commit 由 Git 记录，本文件只保留对交接有价值的结论；
- 不是自动生成的"AI 总结"。脚本提供目录事实与结构，判断类内容（关键决策、下一步）必须由人或实现 Agent 明确写入。

**三条硬边界**：

1. **单一生成逻辑**：阶段四流程与独立调用都执行 `scripts/handoff_record.py`，禁止另写一套模板或手工拼文档；
2. **先取证再落笔**：先读设计文档与项目目录，再写记录；禁止凭对话印象编造进度；
3. **commit 前必须更新或校验**：由 pre-commit 钩子强制，不依赖自觉。

## 2. 两级场景判定（必须先判定）

> **层级关系**：「新会话」不是与「新项目」并列的第三类，而是**已有项目**下的一种会话状态。
> 必须先判断项目处于哪一阶段，再判断当前会话是否保留上文——顺序不可颠倒。

```
第 1 级：是否新项目？（提交数 ≤ 1 且无实现文件）
    ├─ 是 → new-project（阶段四开工，基于设计文档建框架）
    └─ 否 → 已有项目，进入第 2 级
第 2 级：已有项目中，当前会话是否保留了上文？
    ├─ 是（非新会话）→ existing-continue（上下文摘要 + 目录内容）
    └─ 否（新会话）  → existing-new-session（仅目录 + Git 历史）
```

| 层级 | 场景 | 判定条件 | 记录来源 | 命令 |
|---|---|---|---|---|
| 第 1 级 | **新项目** | 提交数 ≤ 1，且除 `docs/`、AGENTS.md 外无实现文件 | 设计文档（MVP 清单 / 技术栈 / 已知风险）→ 建框架 | `init --mode new-project` |
| 第 2 级（已有项目） | **非新会话** | 已越过新项目阶段；当前对话保留了上文 | 上下文摘要 + 项目目录 + Git 历史 | `update --mode continue --context <文件>` |
| 第 2 级（已有项目） | **新会话** | 已越过新项目阶段；对话从零开始 | 仅项目目录 + Git 历史 | `update --mode new-session` |

**判定纪律**：

- **先项目阶段、后会话状态**：不能只凭"是不是新会话"直接选场景——新项目也可能处在新会话中，此时仍是 `new-project`；
- `auto` 的兜底顺序：提交数 ≤ 1 且无实现文件 → 新项目；否则有上下文按非新会话、无上下文按新会话；
- **非新会话必须提供 `--context`**：脚本会拒绝没有上下文的 `continue`，避免"假装合并了上文"；
- **新会话禁止提供 `--context`**：脚本会拒绝，避免把不可靠的记忆混入目录事实；
- **记录是否存在不参与判定**：重复执行 `init` 不会把新项目改判为已有项目；
- 判定结果写入 frontmatter 的 `mode` / `mode_label` 与第 8 节更新记录，事后可审计。

### 2.1 统一框架（不因场景而变）

三种场景**共用同一套模板与同样的九节结构**——场景只决定内容从哪里取证：

| 项目 | 是否随场景变化 |
|---|---|
| 模板（`assets/handoff-record-template.md`） | **不变** |
| 九个小节及其顺序 | **不变**（七节必填 + 更新记录 + 交接提示） |
| frontmatter 字段 | **不变**（仅 `mode` / `mode_label` / `head` / `updated_at` 取值不同） |
| 每节的填写要求与空态约定 | **不变** |
| 内容取证来源 | 变化：设计文档 / 上下文 + 目录 / 仅目录 |
| `mode` 标记 | 变化：`new-project` / `existing-continue` / `existing-new-session` |

脚本在写入前用**同一套** `validate_text` 校验生成结果：缺节、空节、占位符或残留 AUTO 标记都会中止写入，避免某个场景产出"另一种格式"的交接文档。

## 3. 统一文档结构（所有场景同一套：七节必填 + 两节辅助）

| 小节 | 必填 | 内容要求 | 主要来源 |
|---|---|---|---|
| 1. 已完成内容 | 是 | 可验证的完成项，带 commit 短哈希 | Git 历史 + 上下文 |
| 2. 变更范围 | 是 | 版本基线、模块分布、测试、设计输入 | 项目目录 + Git |
| 3. 关键决策 | 是 | 影响后续实现的取舍与理由 | 技术方案 + 上下文 |
| 4. 未完成事项 | 是 | 可勾选清单；完成一项改 `[x]` | 产品设计 MVP 清单 + 上下文 |
| 5. 风险或阻塞 | 是 | 风险 / 阻塞、来源、待处理状态 | 技术方案「已知风险」+ 上下文 |
| 6. 下一步计划 | 是 | 有序步骤，可直接执行 | 上下文优先，缺失时由未完成事项推导 |
| 7. 关联设计文档 | 是 | 文档路径、确认状态、本次引用内容 | `docs/product-design.md`、`docs/tech-design.md` |
| 8. 更新记录 | 否 | 时间 · 场景 · HEAD · 原因 | 脚本自动追加 |
| 9. 交接提示 | 否 | 场景说明与阅读顺序 | 脚本 + 人工补充 |

**空态约定**：尚无内容时必须写显式空态（`（尚无…）` / `（暂无…）` / `（尚未…）`），不得留 `{{占位}}`、`待填写`、`TODO`、`TBD`——`check` 会把占位符判为结构不通过。

**frontmatter 字段**：`record`（固定 `handoff`）、`project`、`mode`、`mode_label`、`branch`、`head`、`updated_at`。

## 4. 阶段四流程接入

### 4.1 开工（进入阶段四的第一件事）

1. 确认 AI 自测能力（阶段一第 5 条）；
2. 按两级判定场景：先分新项目 / 已有项目，已有项目再分非新会话 / 新会话（见第 2 节）；
3. 执行对应命令生成记录，脚本默认安装 pre-commit 钩子；
4. 实现 Agent 的开工提示词改为**先读交接记录**，再读 `AGENTS.md` 与双文档（C-6 / C-9）；
5. 记录随首次提交一起入库，作为后续对比基线。

### 4.2 开发中（每次 commit 前）

二选一，缺一即被钩子拦截：

| 方式 | 命令 | 适用 |
|---|---|---|
| 更新记录 | `python scripts/handoff_record.py update <项目>` | 完成功能、改变范围、新增决策/风险/计划 |
| 仅校验 | `python scripts/handoff_record.py check <项目> --stamp` | 纯重构、注释、格式化等不改变交接信息 |

**更新记录后必须 `git add docs/handoff-record.md`**——钩子只认"记录在本次暂存区"或"本次校验签"，工作区改了但没 add 仍会被拦截。

### 4.3 阶段四 DoD（新增项）

- [ ] `docs/handoff-record.md` 存在且七节齐全（`check` 通过）
- [ ] 记录最后一次更新所在 commit 之后无未记录的代码提交（`check_project.py` H1 通过）
- [ ] 每个可验证功能/修复的 commit 前，均有记录更新或校验留痕

## 5. commit 门禁机制

### 5.1 钩子做了什么

`install-hook` 写入 `.git/hooks/pre-commit`，提交前执行：

```bash
handoff_record.py check <项目> --staged --quiet
```

放行条件（满足其一）：

1. 本次暂存区包含 `docs/handoff-record.md`；
2. `.git/handoff-verified` 中的校验签 HEAD 与当前 HEAD 一致（由 `check --stamp` 写入）。

拦截时输出三条信息：本次暂存文件数、更新记录命令、仅校验命令。

### 5.2 为什么用校验签而不是改记录

- 校验签存放在 `.git/` 内，不进入版本库、不污染工作区；
- 每次 commit 后 HEAD 变化，旧签自动失效——"一次校验只换一次提交"；
- 若每次校验都改记录，会产生无意义的文档 diff，反而降低记录可信度。

### 5.3 钩子安全约定

- 已存在自定义 `pre-commit` 时不覆盖：提示手动合并，`--force` 才备份后替换；
- 非 Git 项目跳过安装，`init` 仍正常生成记录；
- 钩子依赖 Python 解释器：默认 `python`，可用环境变量 `HANDOFF_PYTHON` 指定；
- 不建议 `git commit --no-verify` 绕过；确需绕过时，事后必须补一次 `update`。

## 6. 上下文摘要文件格式（已有项目的非新会话）

`--context` 接受 Markdown，按二级标题归类；未加列表符号的行自动补 `- `：

```markdown
## 已完成内容
- 实现了记账录入与列表展示

## 关键决策
- 数据先本地存储，暂不接后端

## 未完成事项
- [ ] 月度报表按分类汇总

## 风险或阻塞
- 时区处理方案未定

## 下一步计划
1. 补齐月度报表
2. 补充边界用例测试
```

可识别的小节：已完成内容、变更范围、关键决策、未完成事项、风险或阻塞、下一步计划、交接提示。无法识别的标题会被忽略。

**摘要写法**：只写结论与状态，不写过程叙述；每条都能对应到代码、commit 或设计文档。

## 7. 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 每次提交前随手改一行记录应付钩子 | 记录失真，交接时反而误导 | 只写真实进度；纯技术性提交用 `--stamp` |
| 新会话凭印象补写"已完成" | 把记忆当成事实，后续实现基于错误基线 | `--mode new-session`，只写目录与 Git 能证明的内容 |
| 已有项目却不区分会话状态 | 非新会话丢上文，或新会话混入不可靠记忆 | 先判项目阶段，再判会话状态；非新会话用 `--context`，新会话只用目录事实 |
| 非新会话不写上下文摘要 | 丢失只有对话里才有的决策 | 先落 `--context` 文件，再刷新记录 |
| 记录与设计文档冲突时改记录 | 规格漂移，AI 按错误规格实现 | 以设计文档为准；规格问题走阶段二/三修订回路 |
| 手工复制模板另建一份交接文档 | 两套结构，钩子与体检都失效 | 只用 `handoff_record.py`，模板由 `assets/` 权威提供 |
| 记录写完不提交 | 下次会话读不到，等于没写 | 与代码同批提交，或紧随其后单独提交 |

## 8. 参考命令

```bash
# 新项目：阶段四开工，基于设计文档建框架（默认安装钩子）
python scripts/handoff_record.py init . --mode new-project

# 已有项目 · 非新会话（先写上下文摘要文件）
python scripts/handoff_record.py update . --mode continue --context /tmp/context.md

# 已有项目：新会话（只依据目录与 Git 历史）
python scripts/handoff_record.py update . --mode new-session

# 提交前：更新记录（推荐）或仅校验
python scripts/handoff_record.py update .
python scripts/handoff_record.py check . --stamp

# 只校验结构，不写任何东西
python scripts/handoff_record.py check .

# 安装 / 重装钩子
python scripts/handoff_record.py install-hook .

# 演练：输出将生成的内容，不落盘
python scripts/handoff_record.py init . --dry-run
```

退出码：`0` 成功 / 通过；`1` 失败 / 结构不通过 / 被门禁拦截。
